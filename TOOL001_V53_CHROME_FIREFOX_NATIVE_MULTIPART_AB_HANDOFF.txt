TOOL001 V53R2 CHROME vs FIREFOX NATIVE MULTIPART ENGINE BOUNDARY A/B

목적
- V52에서 Chrome native HTML multipart조차 1/7 성공, 6/7 실패했고 실패 회차에서 ERR_UPLOAD_FILE_CHANGED가 확인됨.
- JavaScript byte read / React / Next.js / TOOL001 코드를 모두 제거한 상태에서도 Chrome에서 실패했으므로,
  V53은 같은 최소 HTML + 같은 native multipart + 같은 PHOTO01을 Chrome(Chromium)과 Firefox(Gecko)에서 비교한다.
- 목표는 Chromium Android 업로드 경계인지, 그보다 아래 Android Photo Picker/provider URI 경계인지 한 단계 더 분리하는 것.

사전 조건
- Android Firefox Stable이 반드시 설치되어 있어야 함. 패키지: org.mozilla.firefox
- Firefox를 설치한 직후라면 한 번 직접 실행하여 최초 설정/온보딩 화면을 끝내 둔다.
- runner는 Firefox Beta/Nightly로 자동 fallback하지 않는다. Stable이 없으면 즉시 중단한다.

검수 원칙
- Chrome 7회 + Firefox 7회 = 총 14회
- 두 브라우저 모두 동일한 ADB 흐름으로 최소 HTML 페이지 진입
- 각 회차 브라우저 fresh force-stop 후 시작
- 페이지 중앙을 딱 1회 탭 -> 실제 file input 열기
- V39 원본 Photo Picker 선택 함수 그대로 사용
- 각 회차 PHOTO01 1회 선택
- JavaScript arrayBuffer/FileReader/stream byte read 없음
- 선택 후 HTML form multipart/form-data submit 1회
- 로컬 Node 서버는 adb reverse를 통해 업로드 bytes만 수신/계수
- retry/recovery/다른 사진/fallback 없음
- HARNESS_FAIL은 브라우저/업로드 FAIL과 분리
- TOOL001/React/Next.js 제품 코드 없음

판정 방향
A. Chrome 랜덤 실패 + Firefox 7/7
   -> Chromium Android 파일 업로드/재오픈 경계 문제 강하게 지지
B. Chrome과 Firefox 둘 다 랜덤 실패
   -> Chromium보다 아래 Android Photo Picker/provider URI 전달 계층 의심 강화
C. 둘 다 7/7
   -> 과거 랜덤성 때문에 동일 방식 반복 횟수만 추가
D. HARNESS_FAIL 존재
   -> 브라우저 엔진 결과와 분리. 제품/브라우저 FAIL로 계산 금지
